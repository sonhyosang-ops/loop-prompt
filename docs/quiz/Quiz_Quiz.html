Loop Prompt 문제 풀이

루프 도구·패턴·개념을 NFC 학급 관리 시스템 맥락에서 점검합니다  |  ← 핸드북 홈

학습법: 먼저 스스로 풀어 보고 '정답·해설 보기'를 눌러 대조하세요. 서술형은 자유 서술이라 자동 채점이 없으며, 모범답안·채점 기준(루브릭)과 비교해 스스로 점검합니다. 입력 내용은 저장·전송되지 않습니다.
객관식 개념 확인 도구·메커니즘·패턴의 핵심 특성을 정확히 이해하고 있는지 확인합니다
Q1 객관식 초급
NFC 리더가 매 30초마다 네트워크 상태를 점검해 오프라인이면 Slack 알림을 보내는 작업을 Claude Code에서 구현하려 한다. 다음 중 가장 적절한 도구는?
  1. ①/goal "NFC 리더가 오프라인이면 중지" — 목표 달성 시 자동 종료
  2. ②/loop 30s — 30초 간격 반복 실행
  3. ③/schedule "매 30초" — Anthropic 관리 클라우드 스케줄
  4. ④/loop 300s — 5분 간격 반복 실행
힌트 보기
"주기적·지속적 감시"가 핵심입니다. 목표를 달성하면 멈추는 게 아니라 계속 확인해야 합니다. /schedule은 Anthropic 클라우드 루틴으로 초 단위 간격은 지원하지 않습니다.
정답·해설 보기
정답: ②

② /loop 30s가 정답입니다. 이 시나리오는 "오프라인 감지"라는 반복 폴링 패턴이 필요합니다. /loop [interval]은 지정 간격마다 세션을 재시작해 가장 간단하게 구현됩니다.

  • ① /goal은 "조건 달성 시 종료"이므로 지속 감시가 아닌 한 번의 작업 완료에 적합합니다.
  • ③ /schedule은 분·시간·요일 단위 클라우드 루틴이며 30초 간격을 지원하지 않습니다.
  • ④ /loop 300s는 5분(300초) 간격인데, NFC 상태 점검 요건(30초)을 충족하지 못합니다.
Q2 객관식 중급
자율 속도 루프(/loop 간격 미지정)에서 Claude Code가 내부적으로 사용하는 ScheduleWakeup의 delaySeconds를 설계할 때, 다음 중 피해야 할값은?
  1. ①60초 — 작업이 1분 안에 끝날 때
  2. ②270초 — 프롬프트 캐시를 워밍 상태로 유지하면서 대기할 때
  3. ③300초 — "5분 간격"이라는 라운드 넘버
  4. ④1200초 — 작업이 끝난 뒤 다음 실행까지 충분한 간격이 필요할 때
힌트 보기
Anthropic 프롬프트 캐시의 TTL(Time-To-Live)을 기억하세요. 정확히 그 경계에 걸리면 어떤 일이 생길까요?
정답·해설 보기
정답: ③

300초는 프롬프트 캐시 TTL과 정확히 일치해 worst-case입니다. 캐시가 살아있기에는 너무 길고, 캐시 미스를 감수하고 오래 기다리기에는 너무 짧습니다.

  • ① 60초 이하: 캐시 TTL(5분) 이내이므로 워밍 유지 — 정상.
  • ② 270초: TTL 경계 직전, 캐시 워밍 유지 — 정상.
  • ③ 300초: TTL 경계 정확히 일치 → 캐시 미스 발생, 속도·비용 손실만 얻음 — 피할 것.
  • ④ 1200초+: 의도적 캐시 미스를 감수한 긴 대기 — 정상(장기 주기 작업에 적합).
핵심 키워드: 캐시 TTL 300s 함정 ScheduleWakeup
Q3 객관식 중급
SELF-REFINE 패턴의 실행 순서를 올바르게 나열한 것은?
  1. ①비판(Critique) → 초안 생성(Generate) → 개선(Refine) → 종료 판단
  2. ②초안 생성(Generate) → 비판(Critique) → 개선(Refine) → 종료 판단
  3. ③초안 생성(Generate) → 개선(Refine) → 비판(Critique) → 종료 판단
  4. ④비판(Critique) → 개선(Refine) → 초안 생성(Generate) → 종료 판단
힌트 보기
이름 그대로입니다. 개선하려면 먼저 무언가가 있어야 하고, 개선하기 전에 무엇이 부족한지 알아야 합니다.
정답·해설 보기
정답: ②

SELF-REFINE 논문(Madaan et al. 2023)의 공식 순서는 Generate → Critique → Refine입니다.

  1. Generate: 초안 산출 (예: 학급 출결 보고서 초안 작성)
  2. Critique: 같은 모델이 초안의 약점·누락을 비판
  3. Refine: 비판 내용을 반영해 개선된 버전 생성
  4. 종료 판단: 품질 기준 충족 여부 확인 → 충족 시 종료, 미충족 시 Critique부터 반복
서술형 적용·설명 실제 시나리오에서 올바른 도구와 패턴을 선택하고 그 근거를 논술합니다
Q4 서술형 중급
NFC 리드 기반 학급 관리 시스템에서 다음 두 가지 업무를 각각 Claude Code로 자동화한다고 가정하자.

(A) 학생이 교실에 입장하면 NFC 리더가 태깅 데이터를 attendance.json에 기록하는데, Claude Code가 해당 파일을 매 60초마다 읽어 이상 항목(중복 태깅, 미등록 카드)을 검출하고 담당 교사에게 알린다.
(B) 기말 출결 보고서 초안을 작성하되, 작성 후 자동으로 검토·수정·재검토를 반복해 "누락 항목 없음·형식 오류 없음"이 모두 만족될 때 멈춘다.

각 업무에 가장 적합한 Claude Code 루프 도구를 하나씩 선택하고, 그 이유를 두 가지 이상 제시하라. 다른 도구가 부적합한 이유도 함께 설명할 것.
※ 입력 내용은 저장·전송·채점되지 않습니다. 스스로 정리한 뒤 아래와 대조하세요.
접근 힌트 보기
핵심 차이를 떠올리세요: "언제 멈추나?" (A)는 멈추는 조건이 없고, (B)는 명확한 품질 조건이 있습니다. 각 도구의 종료 방식과 반복 방식을 비교하면 선택이 자연스럽게 결정됩니다.
모범답안·채점 기준 보기

(A) 적합 도구: /loop 60s
이유 ① 이 업무는 "60초마다 파일을 읽고 이상 항목을 알린다"는 무한 반복 폴링이므로, 종료 조건 없이 지정 간격마다 동일 작업을 재실행하는 /loop [interval]이 적합합니다.
이유 ② 이상이 없는 경우에도 계속 실행해야 하므로 "조건 달성 시 종료"하는 /goal을 쓰면 이상이 없는 첫 번째 사이클에서 루프가 끊길 위험이 있습니다.
이유 ③ /schedule은 Anthropic 관리 클라우드 루틴으로 수십 초 단위 간격은 지원되지 않으며, PC가 꺼져도 실행해야 하는 장기 정기 배치에 적합합니다. 교실 실시간 감시처럼 로컬 파일에 의존하는 작업에는 부적합합니다.

(B) 적합 도구: /goal "누락 항목 없음 AND 형식 오류 없음"
이유 ① "조건이 충족되면 멈추는" 목표 지향 루프로, SELF-REFINE(Generate→Critique→Refine)을 자연스럽게 구현합니다.
이유 ② /loop는 고정 간격으로만 반복하므로, 품질 기준 달성 여부와 무관하게 계속 실행됩니다. 보고서가 이미 완성되었어도 반복이 멈추지 않아 불필요한 수정이 발생할 수 있습니다.
이유 ③ /goal에는 max N turns 설정으로 최대 반복 횟수를 제한할 수 있어, 무한 루프 방지와 품질 보장을 동시에 달성합니다.

채점 기준(루브릭)
  • (A)에서 /loop [interval]을 선택하고, "종료 조건 없는 반복"을 언급했는가
  • (B)에서 /goal을 선택하고, "품질 조건 달성 시 종료"를 언급했는가
  • 각각 다른 도구가 왜 부적합한지 구체적으로 설명했는가
  • 두 도구의 핵심 차이(종료 방식)를 비교했는가
핵심 키워드: /loop /goal 폴링 패턴 자기 수정 루프 종료 조건
Q5 서술형 고급
일반 LLM 루프 기법인 SELF-REFINE과 Reflexion은 모두 "자기 수정"을 추구하지만 동작 방식이 다르다. 두 기법의 핵심 차이를 비교 설명하고, NFC 학급 관리 시스템에서 각 기법이 적합한 시나리오를 하나씩 제시하라. 또한 두 기법을 결합하면 어떤 이점이 있는지 서술하라.
※ 입력 내용은 저장·전송·채점되지 않습니다.
접근 힌트 보기
Reflexion의 핵심은 실패 기억입니다. SELF-REFINE이 단일 결과물을 개선하는 반면, Reflexion은 여러 시도에 걸쳐 무엇이 왜 실패했는지 누적합니다. NFC 시스템에서 "한 번의 문서 품질 향상"과 "반복 실수 방지"가 어떤 업무에 맞는지 생각해 보세요.
모범답안·채점 기준 보기

핵심 차이

  • SELF-REFINE은 단일 작업 내에서 Generate → Critique → Refine을 반복합니다. 비판 내용이 같은 세션의 컨텍스트로만 존재하며, 다음 독립 실행 시 초기화됩니다.
  • Reflexion은 여러 시도에 걸쳐 실패 기억(verbal memory)을 외부 메모리(파일·메모)에 누적합니다. 다음 실행 시 이전 실패 원인을 프롬프트에 주입해 같은 실수를 반복하지 않습니다.

NFC 시나리오별 적합 기법

  • SELF-REFINE 적합: 월간 출결 요약 보고서 단건 작성. 초안을 Critique(누락 학생 없는가? 날짜 오류 없는가?)해 즉시 Refine — 한 번 완성하면 충분한 작업에 적합합니다.
  • Reflexion 적합: 이상 태깅 탐지 쿼리 개선. 매주 새 데이터에 쿼리를 실행할 때마다 탐지 실패 사례를 기록하고 다음 주 쿼리에 반영 — 반복 실수를 누적 학습으로 방지합니다.

결합 이점

SELF-REFINE으로 즉각적 품질을 높이고(세션 내 Critique·Refine), Reflexion으로 장기 개선을 누적합니다(세션 간 실패 기억). 예: 매주 보고서를 SELF-REFINE으로 작성하되, 반복되는 오류 유형(예: 특정 반 데이터 누락)은 Reflexion 메모에 기록해 다음 주 초안 생성 시 프롬프트에 주입하면 같은 실수가 줄어듭니다.

채점 기준(루브릭)
  • SELF-REFINE과 Reflexion의 동작 차이를 "세션 내 vs 세션 간"으로 명확히 구분했는가
  • Reflexion의 핵심인 "외부 메모리 누적"을 언급했는가
  • NFC 도메인 시나리오가 각 기법의 특성과 논리적으로 연결되는가
  • 결합 이점을 구체적으로 서술했는가(단순 나열이 아닌 시너지 효과)
핵심 키워드: SELF-REFINE Reflexion verbal memory 세션 간 누적

Q6 Q&A
/loop와 /schedule은 둘 다 반복 실행인데, 어떻게 다른가요?
답 보기

두 도구는 실행 위치와 지속성이 다릅니다.

  • /loop: 로컬 PC에서 현재 세션 안에 반복합니다. PC를 끄거나 터미널을 닫으면 중단됩니다. 초·분 단위 짧은 간격이 가능합니다.
  • /schedule: Anthropic 클라우드가 관리하는 루틴으로, PC가 꺼져도 지정 시각에 실행됩니다. 매일·매주 같은 장기 주기에 적합하며, 로컬 파일에 직접 접근하는 작업에는 제한이 있습니다.

선택 기준: 로컬 파일·실시간 감시 → /loop, 클라우드 리소스 대상 정기 배치(보고서 생성, API 호출 등) → /schedule.

Q7 Q&A
실수로 무한 루프(/loop)를 걸어 버렸습니다. 어떻게 중단하나요?
답 보기

세 가지 방법이 있습니다:

  1. 루프 프롬프트에서 "stop" 입력: 루프가 대기 중일 때(다음 세션 시작 전) stop 또는 clear를 입력하면 중단됩니다.
  2. /goal stop 또는 /goal off: /goal로 실행 중인 루프라면 이 명령으로 취소합니다.
  3. 터미널 강제 종료: Ctrl+C로 현재 세션을 종료하면 루프가 즉시 멈춥니다. /loop는 로컬 프로세스이므로 프로세스 종료로 언제든 중단 가능합니다.

/schedule로 등록한 클라우드 루틴은 /schedule cancel [ID] 또는 Claude.ai 설정 화면에서 삭제합니다.

Q8 Q&A
ScheduleWakeup에서 정확히 300초를 쓰면 안 된다고 하는데, 왜 300초가 문제인가요?
답 보기

Anthropic 프롬프트 캐시의 TTL(Time-To-Live)이 5분(300초)입니다. delaySeconds=300을 지정하면 캐시가 딱 만료되는 시점에 깨어나 캐시 미스가 거의 확실히 발생합니다.

  • 캐시 워밍 상태 유지를 원한다면 ≤270초를 사용하세요.
  • 긴 대기로 캐시 미스를 의도적으로 감수하는 경우라면 ≥1200초로 넉넉히 주면 비용 대비 효율이 좋아집니다.
  • 300초는 "캐시도 못 유지하고, 긴 대기의 이점도 없는" 최악의 선택입니다.
Q9 Q&A
NFC 출결 시스템에서 루프 패턴을 처음 설계할 때 흔히 저지르는 실수는 무엇인가요?
답 보기

실제로 자주 보이는 실수 세 가지:

  1. 폴링과 목표 루프 혼용: "이상 없으면 멈춰라"는 뜻으로 /goal을 폴링에 쓰면, 첫 번째 이상 없는 사이클에서 루프가 끊깁니다. 지속 감시에는 반드시 /loop [interval]을 사용하세요.
  2. 루프 내 부수 효과 누적: 루프마다 파일에 로그를 덮어쓰지 않고 추가(append)만 하면 파일이 무한정 커집니다. .claude/loop.md에 "로그는 최근 N개만 유지"를 명시하거나, 외부 로그 관리 도구를 함께 쓰세요.
  3. 종료 조건 없는 /goal 루프: 품질 기준이 너무 엄격하면 루프가 최대 반복 횟수까지 계속 돌아 불필요한 API 비용이 발생합니다. 항상 max N turns를 설정해 상한을 지정하세요.
Q10 Q&A
Claude Code에서 /goal을 사용할 때 종료 조건을 어떻게 작성해야 효과적인가요?
답 보기

효과적인 종료 조건의 세 가지 원칙:

  1. 검증 가능하게: "보고서가 완성되면"처럼 모호한 조건 대신, "check_report.py 가 exit 0으로 종료되면"처럼 스크립트나 커맨드 결과로 판단할 수 있게 작성하세요.
  2. AND 조건으로 복합 품질 보장: "누락 항목 없음 AND 형식 오류 없음 AND 총 행 수 ≥ 30"처럼 여러 품질 기준을 AND로 연결하면 한 조건만 통과해 조기 종료되는 것을 방지합니다.
  3. 반드시 최대 반복 수 지정: /goal "..." max 8 turns처럼 상한을 두어 무한 루프와 과도한 비용 발생을 방지하세요. NFC 출결 보고서처럼 반복 비용이 큰 작업일수록 중요합니다.

자세한 내용은 Tools 매뉴얼 → /goal을 참조하세요.
