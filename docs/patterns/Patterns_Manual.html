패턴 선택 가이드

루프를 설계할 때 가장 먼저 결정해야 할 것은 "무엇을 기다리는가"다. 답에 따라 아래 네 가지 패턴 중 하나를 선택한다.

패턴핵심 질문중단 조건사용 도구
폴링외부 시스템 상태가 바뀌었는가?상태 변화 감지 또는 취소/loop
자기 수정내 출력이 기준을 충족하는가?검증 통과 또는 최대 시도/goal
목표 지향정의된 완료 기준에 도달했는가?기준 충족 또는 턴 제한/goal
멀티 에이전트병렬로 처리할 독립적 작업이 있는가?모든 에이전트 완료Agent + /goal

1. 폴링 패턴 (Polling Pattern)

폴링 외부 상태를 주기적으로 확인해 변화에 반응하는 패턴
외부 시스템(API, 파일, 프로세스)의 상태 변화를 기다리거나 이상을 감지해야 할 때. 변화를 즉시 알 수 없고 주기적으로 확인해야 하는 상황에 적합하다.

구조

# 기본 폴링 구조
/loop [interval] [상태 확인 프롬프트]

# 예: NFC 리더 상태 폴링
/loop 60s GET /api/reader/status 를 호출해서 상태를 확인하고,
"connected" 이외의 상태면 관리자에게 Slack 알림을 보내줘

인터벌 설계 원칙

인터벌은 실제 변화 주기를 고려해 설정한다. 너무 짧으면 불필요한 API 비용과 속도 제한이 발생하고, 너무 길면 변화를 놓친다.

상황권장 인터벌이유
NFC 리더 상태 확인30s – 60s연결 끊김을 빠르게 감지해야 하지만 초 단위 변화는 아님
CI/CD 빌드 완료 대기60s – 120s빌드는 보통 수분 걸림, 짧은 폴링은 낭비
배포 완료 대기120s – 270s배포는 수분~수십 분, 캐시 유지 범위 안에서 최대한 길게
일일 보고서 생성/schedule 사용시간 기반 트리거는 클라우드 루틴이 더 적합
폴링 루프에 "이상이 발견되면 X를 실행해줘" 같은 지시를 포함할 때는, 조치 범위를 명확히 제한해야 한다. 범위가 넓으면 의도치 않은 수정이 발생할 수 있다.

2. 자기 수정 패턴 (Self-Correction Pattern)

자기 수정 출력을 검증하고 기준 미달 시 스스로 수정을 반복하는 패턴
생성된 결과물(코드, 데이터, 문서)이 정해진 기준을 충족해야 하며, 자동화된 검증 도구가 있을 때. NFC 출석 데이터 무결성 검사처럼 통과/실패가 명확한 상황에 적합하다.

구조

# 기본 자기 수정 구조 (/goal 활용)
/goal [검증 기준이 충족될 때까지 수정], 최대 N번 시도

# 예: 출석 데이터 무결성 수정
/goal bash validate_attendance.sh 실행 결과에 오류가 없을 때까지
attendance.json의 중복·누락을 수정해줘. 최대 10번 시도 후 멈춰

효과적인 자기 수정 루프의 요건

  1. 외부 검증 도구: 주관적 판단이 아니라, 스크립트·테스트·린터처럼 명확한 기준을 제공하는 도구가 있어야 한다
  2. 최대 시도 횟수: 무한 루프를 방지하기 위해 반드시 상한선을 설정한다
  3. 실패 보고: 최대 시도를 소진하면 해결하지 못한 항목 목록을 보고하도록 지시한다
자기 수정 루프는 파일을 반복 수정할 수 있다. 실행 전에 git commit 또는 백업으로 원본을 보존해야 한다.

3. 목표 지향 패턴 (Goal-Oriented Pattern)

목표 지향 달성 기준을 명시하고 에이전트가 자율적으로 방법을 선택하는 패턴
목표(what)는 명확하지만, 달성 방법(how)은 에이전트가 유연하게 선택해야 하는 상황. 여러 접근법을 시도해볼 수 있는 탐색적 작업에 적합하다.

구조

# 기본 목표 지향 구조
/goal [달성해야 할 상태를 기술], [안전장치: 턴 제한·금지 사항]

# 예: NFC 시스템 성능 목표
/goal classroom-nfc API의 응답 시간이 200ms 이하가 되도록 최적화해줘.
데이터베이스 스키마 변경이나 의존성 추가 없이, 최대 5번 시도 후 중단해줘

좋은 목표 기술의 요소

요소예시목적
측정 가능한 완료 기준"응답 시간 200ms 이하"에이전트가 완료 여부를 판단할 수 있게
행동 제약"스키마 변경 없이"의도치 않은 범위 확장 방지
시도 횟수 상한"최대 5번 시도"무한 루프 방지
실패 처리"해결 못하면 목록 보고"결과의 가시성 확보

4. 멀티 에이전트 루프 (Multi-Agent Loop)

멀티 에이전트 여러 에이전트가 병렬로 독립적 작업을 처리하는 패턴
처리해야 할 작업이 여러 개이고 서로 독립적일 때. NFC 리더가 여러 교실에 설치돼 있거나, 여러 학급의 출석 데이터를 동시에 검증해야 하는 상황에 적합하다.

구조

# 병렬 에이전트로 여러 학급 출석 데이터 동시 검증
각 학급(1학년~3학년) 폴더의 attendance.json 파일을 동시에 검증해줘.
각 학급은 독립적인 서브에이전트가 처리하고, 모두 완료되면 결과를 합산해 보고해줘

멀티 에이전트 루프 설계 원칙

  1. 독립성 확인: 각 에이전트의 작업이 서로 영향을 주지 않아야 한다. 같은 파일을 동시에 수정하면 충돌이 발생한다
  2. 결과 집합: 모든 에이전트가 완료된 뒤 결과를 통합하는 주체(오케스트레이터)를 명시한다
  3. 오류 격리: 한 에이전트의 실패가 전체를 중단시키지 않도록 각 에이전트는 독립적으로 오류를 처리한다
멀티 에이전트 루프는 API 비용이 단일 에이전트보다 빠르게 증가한다. 병렬화의 이점이 비용을 상회하는지 먼저 소규모로 검증할 것.
